# Flood Event Agent：首版端到端原型计划

日期：2026-09-24

实施状态（2026-10-09）：v0.1 基线与 30 年目标窗口逐日查询已完成；历史数据实际只覆盖 2025-05-22 至 2026-10-07，不能据空响应断言早年无洪水。reading 级 LLM→GIS baseline 已对固定 16 条样本执行一次；自动证据校验通过 11 条，5 条因路径格式不符未通过，尚无人工准确率。详见 `PROJECT_PROGRESS.md` 与 `README.md`；本地数据和生成报告不随代码发布。道路核对仍只有合成情景，真实道路影响尚未验证。以下保留最初端到端原型计划，作为后续对照。

## 目标与边界

输入为 [data.gov.sg 的 PUB 洪水警报接口](https://api-open.data.gov.sg/v2/real-time/api/weather/flood-alerts)；输出为可被地图读取的警报地点 GeoJSON、可回放的消息时间线，以及供路由模块使用的**经人工核对的道路段**。首版同时支持实时查询和本地回放。即使当前没有洪水警报，也能正常输出空图层和明确的更新时间。

这个 Agent 不预测积水范围，也不把 API 的广播半径变成避让区。没有核对的地点解析结果可以显示为候选，但不能当作已确认的道路影响。

## 输出契约

| 产物 | 最小内容 | 使用方 |
| --- | --- | --- |
| 原始快照 | 请求参数、抓取时间、响应状态、原始 JSON；失败时记录错误 | 审计、回放、问题定位 |
| 规范化消息 | `message_key`、官方标识（若有）、消息类型、取消引用、发布时间、抓取时间、原文和原始记录引用 | 状态计算、按消息统计 |
| `FeatureCollection<Point>` | 每个 `reading` 对应一个 `reading_key` 和位置；属性包含 `message_key`、状态、地点说明、广播半径、来源和质量标记 | 地图与按警报地点统计的图表 |
| 已核对道路段 | 警报关联、道路段文字、人工核对依据、几何、核对状态、适用时间 | 路由暴露检查及明确标注的绕行情景 |

位置字段应明确命名为 `alert_broadcast_center`；`broadcast_radius_km` 只作为属性保存。若坐标无效或缺失，保留非空间消息并标记原因，不伪造地图位置。

首版使用一个本地 SQLite 文件保存快照、规范化消息和地点，并从中导出 GeoJSON。这样实时模式与回放模式使用同一份记录，重复抓取也容易检查。保留原始响应，避免字段变化后无法重新处理。`message_key` 标识一次警报消息，`reading_key` 标识其第几个地点；真实洪水事件的归并需要额外证据，首版不强行生成 `event_id`。

## 实施顺序

### 1. 固定输入与接口契约

- 记录实际响应层级、`date` 与分页参数、时间字段和空 `readings` 的含义。
- 准备三类可重复输入：无警报快照、有警报快照、字段缺失或类型变化的旧记录。案例均标明来源；人工构造的状态样例显式标“示范情景”。
- 约每 2 分钟查询一次，允许配置频率；处理分页、超时、限流与暂时失败，并显示最后一次成功抓取时间。[data.gov.sg 限流文档](https://guide.data.gov.sg/developer-guide/api-overview/api-rate-limits)

### 2. 保存并规范化事件

- 原始快照先落盘，再解析 `data.records[].item.readings[]`；空 `readings` 产生 0 条事件。
- 将 `area.circle` 中的字符串/数字统一转换为数值，校验纬经度范围；保留 `areaDesc`、正文、严重程度和原始值。
- 分开保存 PUB 发出时间、接口更新时间与本地抓取时间，统一用于比较的时区为 `Asia/Singapore`，同时保留原始时间表示。
- 优先用官方 `identifier` 区分消息；缺失时生成稳定的本地键并标记“无法可靠关联取消消息”。一条消息可有多个 `readings`；给每个地点分配稳定的 `reading_key`。重复轮询同一消息不得重复计数。
- 用 `Cancel.references` 关联被取消的 `Alert`；过期字段若出现则保留为可选信息。状态只对**本地已观测的消息窗口**计算，并记录观测起点；冷启动、缺失取消消息或字段不足时输出 `unknown`，不把“未见取消”直接说成“全岛仍有警报”。

### 3. 生成 GIS 图层与道路候选

- 直接使用 API 中已有的坐标生成 WGS84 GeoJSON 点，注明它代表广播中心；校验坐标是否位于合理的新加坡范围。GeoJSON 坐标顺序是 `[lon, lat]`，与 API 的 `[lat, lon, radius_km]` 不同。[GeoJSON 规范](https://datatracker.ietf.org/doc/html/rfc7946)
- 从 `areaDesc` 和警报正文提取道路、路口和“从……到……”等文本线索；LLM 只输出结构化候选及原文证据，不直接生成道路几何、积水面或封路结论。
- 首版选一个可公开核对的案例，人工记录对应道路段几何、核对人/时间与依据。若无法核对，地图仍可展示警报点，路由输入保持为空。自动生成道路段几何留到后续迭代。

### 4. 接入端到端演示

- 地图模块读取 GeoJSON，按时间和状态筛选点、显示原始描述；直方图分别统计去重消息数或警报地点数，标明口径，不统计轮询次数，也不称其为真实洪水事件数。
- 路由接入准备 [OneMap 认证 token](https://www.onemap.gov.sg/apidocs/authentication)并处理过期。传入起终点时使用 `纬度,经度`；解码返回的路线几何后，结合道路名称、层级/高架情况和空间位置核查是否经过已核对道路段。仅凭点线邻近不判定道路受阻。[OneMap Routing 文档](https://www.onemap.gov.sg/apidocs/routing)
- 实时页面显示“最后成功更新”“本地观测起点”“本系统已观测且未见取消的消息数”“位置/状态不确定数”。该数字不代表全岛真实有效警报总数。回放页面从本地快照按时间重放，确保演示可重复。
- 绕行路线若由额外的候选点或其他方法生成，须再次做空间检查；对比结果标为**情景模拟**。OneMap 驾车路线没有避让区或出发时间参数，因此不同警报时间窗的比较不是 OneMap 的时变交通预测。[OneMap Routing 文档](https://www.onemap.gov.sg/apidocs/routing)

## 首版验收标准

1. 同一批原始快照重复处理，得到相同的消息数、地点数、状态与 GeoJSON；重复轮询不增加计数。
2. 空 `readings` 输出空 `FeatureCollection`；缺字段和字符串坐标不会导致整个流程失败，并产生可读的质量标记。
3. 有效点能与新加坡底图对齐；广播半径从未被表示为淹水区域。
4. 可追溯每个地图点到原始快照、原文和处理时间；可以按指定时间回放。
5. 有 `Alert → Cancel` 证据时状态和有效时间正确；缺少关联证据时显示 `unknown`。
6. 地图和直方图能使用输出契约，且统计口径清楚；路由模块只接收有核对记录的道路段，并能区分真实警报与演示情景。

## 后续研究验证

首版完成后，建立人工核对的地点—道路段样本，比较固定规则、LLM Agent 和人工核对结果。主要指标为地点匹配准确率、无法判断时的正确弃答率、事件去重/取消关联准确率，以及处理延迟和成本。这会检验 Agent 的实际增益，而不仅是展示一个能调用 API 的界面。
