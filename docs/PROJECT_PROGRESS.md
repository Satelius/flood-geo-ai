## 项目目标

教授的首个任务是把 PUB 的新加坡洪水警报与 OneMap 路线服务连接起来，演示洪水事件的地图展示、路线暴露判断和绕行情景，并研究 LLM Agent 在数据整合与判断中的作用。当前先规划 Flood Event Agent：查询、保存、定位并整理警报，给后续地图与路由模块提供可追溯的 GIS 数据。

本目录已有研究提案 `Full Proposal.pdf` / `proposal.txt`。现已完成 v0.1 本地基线原型，代码、测试、实验结果和中文报告均保存在本目录。

## 已确认的接口事实

- [PUB 洪水警报数据集](https://data.gov.sg/datasets/d_f1404e08587ce555b9ea3f565e2eb9a3/view)提供实时 flood alert events，页面标注约每 2 分钟更新；不包含 flood warning notices。
- [洪水警报接口](https://api-open.data.gov.sg/v2/real-time/api/weather/flood-alerts)的响应包含 `data.records[].item.readings[]`。`readings=[]` 的记录不等于一次洪水事件。
- `readings[].area.areaDesc` 是地点文字；`readings[].area.circle` 的顺序为纬度、经度、公里半径。半径表示**警报广播范围**，不是实际淹水范围。
- 警报消息可能包含 `item.identifier`、`item.msgType`（`Alert` / `Cancel`）及 `item.references`。历史响应中曾观察到这些字段缺失，且 `circle` 数值以字符串返回；解析时须允许缺失并记录质量标记。
- 接口支持 `date` 和分页，但官方未承诺完整历史档案或保留期限。实时模式应自行归档；回放必须注明数据来源。
- [GeoJSON 标准](https://datatracker.ietf.org/doc/html/rfc7946)的点坐标顺序为经度、纬度。将 API 的位置写入 GeoJSON 时必须调换顺序。
- [OneMap Routing 文档](https://www.onemap.gov.sg/apidocs/routing)提供起终点路线及距离、时间、编码后的路线几何；调用需要认证。公开的驾车参数中没有“避开区域”或出发时间输入。起终点使用 WGS84 `纬度,经度`，与 GeoJSON 的顺序相反。[OneMap 底图](https://www.onemap.gov.sg/apidocs/maps)使用 EPSG:3857，前端地图可将 WGS84 GeoJSON 叠加显示。

## 当前决定

1. 首版 GIS 主输出采用 **WGS84 GeoJSON 点**。点表示“警报广播中心”，属性保留广播半径、原文、时间、状态、来源与定位质量；不把广播圆命名为洪水范围。
2. 保留原始 API 响应和抓取时间。规范化事件与原始记录建立关联，以支持核查和回放。
3. 对正文中的道路描述，Agent 可以提出候选受影响道路段；首版只有经人工核对的候选道路段才提供给路由演示。它仍应被标为情景假设，除非有独立证据证明道路实际封闭或积水边界。
4. 路由演示先比较 OneMap 常规路线与警报位置/核对道路段的空间关系。绕行需要额外的候选路线方法，不能声称 OneMap 已提供避洪区域参数，也不能仅凭路线差异推断真实交通拥堵。
5. Agent 的研究价值放在地点文字解析、异常处理、证据整理和工具协调；坐标转换、事件去重、状态计算与空间验证使用可复现的确定性规则。
6. 区分 API 快照、警报消息、消息中的地点和真实洪水事件。首版直方图只承诺统计去重后的**警报消息**或**警报地点**，并标明口径；没有充分关联证据时不声称统计了真实洪水事件数。

## Reading 级 Flood Event Agent baseline（2026-10-09）

按已批准的实施计划，从本地固定 manifest 的 16 个 reference 读取原始 SQLite snapshot；不扫描全库、不采集新数据、不改数据库 schema。每个 Responses API user 输入只含一条完整原始 `item.readings[i]`；外层 item/record 只作为代码侧来源属性。由代码保留官方字段并用 `area.circle` 生成 WGS84 广播中心点，LLM 只补道路/地点关系、洪水状态、通行提示和正文时间线索。manifest、数据库和运行产物不随代码发布。

真实运行 `20261009T071523Z-ecb1a8a0` 使用 `gpt-6-luna`、reasoning `medium`，固定上限 16 次，实际发出 16 次请求。封账统计：11 条通过结构与证据自动校验，5 条为 `evidence_error`，0 条未尝试或结果未知；16 条均生成官方 Point。5 条失败项的原始输出均使用 `/description` JSON Pointer，而 validator 只接受计划约定的 `$.description` 路径。它们的语义尚未由人工确认，自动状态不能解释成语义错或语义对。模型用量为输入 9,671、输出 8,338、总计 18,009、推理 4,089 tokens。没有重试或对失败项补调。

中文报告与交互标注页面由本地运行产物生成，不纳入代码仓库；原始响应、逐条 GIS 记录、GeoJSON、manifest 与运行摘要保存在本地。报告页绑定 run ID、manifest SHA 与封账结果 SHA，不包含 API 密钥。运行时生成的 `review.html` 是封账哈希的一部分；`implementation-report.html` 从同一封账结果额外渲染，不改写最终结果。

当前 16 条仍是探索性小样本，不是独立金标数据集。记录级人工标签为 0/16；完成人工审阅前不报告准确率、P/R/F1。广播中心 Point 不等于积水范围；本实现没有道路段匹配、路线避让或交通影响测量。

### 30 年历史回填完成（2026-10-09）

用户已授权把已完成的两年试点扩充为最近 30 年，并要求若接口不支持则按整年缩短窗口。执行计划和最终结果记录在 `HISTORY_BACKFILL_30Y_PLAN.md`。目标为 1996-10-08 至 2026-10-07，共 10,957 天。

官方 PUB 接口按单日查询并支持分页；没有多日范围参数，也没有公布历史保留期限。此前两年批次已完成 730/730 天，6 天有非零警报消息，最早非零日为 2025-05-22。边界预检查询 1996-10-08 返回 HTTP 200、业务 code=0、空 records；这只说明单日请求被接受，不能证明整个历史档案完整或现实中无洪水。新计划要求继续把失败、不可用、未完成日期标为未知，并在报告中说明该限制。

执行前发现并修复回填批次原有 800 天上限，统一为 12,000 天；热力图按日期索引覆盖结果，并限制超大自定义区间。此前 73 项测试、JavaScript 语法检查、Python 编译检查通过，独立复核未发现启动阻塞。批次 `5bef63d4c09d465287bc14a43aa1cfcb` 现已完成：10,957/10,957 日、6 个含警报消息日、10,951 个无规范化非 Cancel 消息日，0 个失败或未完成日；共 21,180 页及 262,869 条原始 records。逐日审计得到 8 条非 Cancel 消息（7 Alert、1 类型不明）和 8 个地点条目。367 个请求日期有原始 records，其中 361 日无非 Cancel 消息、6 日有消息；另有 10,590 日原始 `records` 数组为空。

这个结果不能称为 30 年洪水历史：record.datetime 实际只覆盖 2025-05-22 至 2026-10-07；空 records 及完整查询都不证明早年没有洪水。重新生成的 30 年窗口语料画像包含 262,869 条去重 records，其中 262,853 条没有 readings，只有 16 个地点条目。有限样本道路描述规则命中为 from-to 10、地标邻近 2、括号内容 12、道路关系词 16（可重叠），尚不代表完整类别或道路段匹配。批次审计与本地 archive 消息表分别为 8 与 9 条非 Cancel 消息；差出的 1 条是旧 archive 快照中的同文同地未知类型消息，消息键不同，报告分别保留两种口径。中文网页和 Markdown 结果已更新；原两年抽样 JSON 保留不动。
